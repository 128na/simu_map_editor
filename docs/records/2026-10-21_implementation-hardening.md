# 公開後の実装改善と持続性能計測

## 目的と判断基準

開発ポリシーの段階的リファクタリング方針に基づき、検証を補強してから責務分離・待機描画削減を進めた。Actionsの重複実行を避け、変更をまとめたPRで検証する。

## 実施した検証

- 本番履歴Workerの2チャンク書込み成功後にトランザクションを中断し、既存データ・チャンク・manifestの完全一致、新規レコード不在、後続処理成功を確認した。
- 原子性を壊すテスト配信時の変異では新しい検証が失敗し、変異撤去後は成功した。本番に障害注入APIは追加していない。
- キー操作とカメラ移動を分離し、既存の造成・キー操作14ケースがChrome・Edgeで成功した。
- 描画休止後も造成・設定・表示の24ケースが成功。追加の実WebGL／画素検証6ケースで静止・再描画・逆向きキー解放・可視性復帰を確認した。
- 描画スケジューラの単体4ケースで通知集約・慣性継続・再通知・休止復帰を確認した。

## 待機時の比較

同じWindows端末、Chrome、128四方の初期地形で、初期表示が落ち着いた後のWebGL描画API呼出しを約1秒ずつ3回数えた。変更前は60・61・60回、変更後は0・0・0回だった。これは静止中の描画削減の確認で、ドラッグ速度や消費電力の直接計測ではない。

## 持続負荷の実測

ローカルのChrome、RTX 4070 Ti / D3D11、4096四方の平坦地形、半径40・強さ1で、実マウスの9点ドラッグを盛土・掘削交互に繰り返した。ウォームアップの除外は行わず、60秒と最低12サイクルの両方を満たすまで実行した。62.651秒で55サイクル、Undo/Redoの標高・格子照合19回が成功した。

| 指標 | 前半18サイクル | 後半19サイクル |
| --- | --- | --- |
| ドラッグ中央値 | 187.56 ms | 178.68 ms |
| ドラッグp95 | 385.39 ms | 339.04 ms |
| Undo中央値 | 1216.40 ms | 1191.34 ms |
| Redo中央値 | 1212.29 ms | 1187.34 ms |
| 履歴同期登録中央値 | 0.20 ms | 0.20 ms |
| 履歴patch作成中央値 | 3.40 ms | 2.70 ms |

前半／後半は経過時間の等分ではなく、サイクル数を三分割した先頭・末尾の群。参考JSヒープは最初735.39 MiB、最後730.53 MiB、観測ピーク878.73 MiBだった。履歴保存量は0.284 MiBから15.589 MiBへ増加した。

生データはローカルの `.validation/sustained-sustained-chrome-4096-1792568136519.json` に保存した。計測コードの内容SHAは `17ac42b9752cbfe1d5901d9414c9fd475d1a3df6fa3bce5e5d86052e859e2a85`。以後、JSONに時刻基準と集計群の定義を追記するよう記録形式を補強したが、測定経路は変更していない。

## 限界と次の判断

単一端末・平坦地形・約1分・1試行の結果であり、時間経過による悪化は観測しなかったが、他の地形や長時間操作の安定性を保証しない。JSヒープはGPU・Worker・多くのArrayBufferを含まず、総メモリやリーク否定の根拠にはできない。フレーム間隔にはUndoやダイジェスト検証中も含まれ、描画fpsとは異なる。

今回の同期履歴登録時間だけを根拠にWorkerへの転送方式を変える理由は得られなかった。未保存履歴の所有権と失敗時のRAM保持を維持し、より大きい変更量や長い時間の計測を今後の比較条件とする。

[公開ゲートの判断](../adr/0019-complete-validation-before-pages.md)と[描画休止の判断](../adr/0020-render-on-invalidation.md)に理由を記録した。
