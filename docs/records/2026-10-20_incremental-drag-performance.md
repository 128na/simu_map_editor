# 4096四方のドラッグを1秒以下にする局所更新

## 目的と受け入れ条件

利用者の目標「ドラッグ操作1秒以下」を、既存の4096四方・7点・48タイル移動、半径8・強さ1の自動ドラッグで評価した。Windows、i9-12900F、RTX 4070 Ti、Chrome/Edge、平坦地・海面−2、Linear/係数1/斜面1。Playwrightの入力・通信・待機も含む一連の操作時間で、単一イベントの遅延やGPU完了までの時間とは同一ではない。

## 変更した理由と内容

従来は合法な小編集でも全地図のbaseline・斜面補正・表示格子・量子化集計・水面・メッシュ差分探索を毎回処理していた。

新しい局所造成は、到達可能な整数標高と8近傍の斜面条件を検証し、immutableなHeightmapとprofile値ごとに検証結果をWeakMapへ保存する。標高幅/最大斜面を超える距離では造成の影響が及ばないことを利用し、ブラシ経路に十分なhaloを足した範囲で従来処理を実行する。未正規化・小数・到達範囲外の画像は従来全体処理へ戻す。既存applyBrushは参照実装として維持した。

合法なsourceなら表示格子は標高+1と右・下外周複製だけで全体正規化と一致するため、変更範囲を差分反映する。表示用格子と標高の全配列コピーは残る。合法標高の量子化差分はゼロなので再集計を省略する。水面は隣接cellが全てdryのまま、又は全てwetのままで被覆が変わらない場合に再利用し、海岸が変わる場合は従来再生成と予算チェックを使う。メッシュは指定dirty範囲と隣接法線のみ更新する。バッチのdirty和集合とfallback条件を合成し、未送信GPU範囲も保持する。

## 実測結果

直前の約6,779 msから、Chromeの3回再測定は584 / 591 / 585 ms（中央値585 ms）となった。Edgeでも586 ms。いずれも `DRAG_BUDGET_MS=1000` の失敗判定を有効にして成功した。初回合法性検証も経路に含まれる。3回は毎回新しいブラウザページで同じ前処理から開始した。

[生データ](2026-10-20_incremental-drag-results.json)を保存した。計測時点は親コミットf8597baに今回の未コミット変更を適用した作業ツリーであり、JSONのrevisionは親SHAを指す。最初の試測定605 msも目標を満たしたが、集計には3回再測定を使用した。

## 正しさの検証

単体45件が成功した。4変換mode・係数1/2・斜面1/2、最大上下振幅、中央/外周を含む追加128ケースでhaloより広い地図を使い、従来全処理の全標高配列・変更数・書出格子との一致を確認した。連続編集、raw fallback、profile変更、no-op、格子外周、水面再利用、dirty法線とGPU範囲も検証した。

Chrome・Edgeのnative格子照合を含む通常24件と4096性能判定2件が成功した。lint・型チェック・本番ビルドも成功した。レビューでは合法性、halo、格子+1、バッチ合成、水面判定とGPU範囲にMust/Shouldなしとの確認を得た。最終レビューの残り確認はレビュー担当の利用枠終了で完了していないため、その後はメインで差分を確認した。

## 再実行と制約

PowerShellで `VALIDATE_OPERATIONS=1`、`PERF_SIZES=4096`、`DRAG_BUDGET_MS=1000` を設定し、`npm run test:browser -- --grep 'operation performance' --project chrome` を実行する。閾値は指定時だけ有効で、ソフトウェア描画のCIへ1秒を強制しない。計測の作業条件は変えずbrowser-v1を維持する。

全端末・全地形・全半径で1秒以下を保証したものではない。未正規化画像の初回造成、海岸形状の変更、大きな変更領域や長いドラッグ経路は全体処理又は広い局所処理になりうる。Undo/Redoは全体再構築のままで、メモリ約960 MiBの地形メッシュと全標高履歴も変更していない。局所更新に渡したHeightmapを外部から変更しないことがcacheの前提であり、アプリは既存mapを直接変更せず新しい配列を返す方式を維持する。
