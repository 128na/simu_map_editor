# 初期地形の外周側面修正と連続造成の更新時間

## 目的 / 発端

利用者から128四方が深い直方体に見えることと、4096四方の連続操作がまだ重いとの報告があった。操作全体が1秒以内という従来の目標だけでは、操作中の引っかかりを評価できない。

## 分かったこと（事実）

前回のLOD導入で、全チャンクの全周に高さ−256までのスカートを付けていたことが表示原因だった。スカートをマップ内部のチャンク境界だけに限定し、マップ外周には付けない構成へ修正した。128四方の平坦地の全頂点高さ・三角形数を検証し、Chromeの画像でも深い側面がないことを確認した。

連続造成では、詳細チャンクを毎回作り直していた。同一寸法・同じ海面と表示間隔でのdirty更新を、既存のposition/color/normal配列とGPUバッファの部分更新へ変更した。内部スカートと境界法線も更新し、完全な再生成との配列一致を検証した。表示格子への変換時にsourceの合法性が確認できた場合は、初回造成の全近傍再走査を省くキャッシュを登録する。

4096四方・平坦・半径8・41点の連続ドラッグをChrome/RTX 4070 Tiで旧版d530c64と修正後の処理へ3回ずつ行った。旧版の2モジュールへ実際に差し替えが行われたことも検査した。各試行の指標の中央値は以下のとおり。生データは[計測結果](2026-10-20_interaction-latency-results.json)に保存した。

| 指標 | 修正前 | 修正後 |
|---|---:|---:|
| 初回更新 | 223.0 ms | 28.1 ms |
| 移動更新の中央値 | 26.7 ms | 21.6 ms |
| 移動更新の95%点 | 44.1 ms | 26.0 ms |

描画更新の中央値は約5.6→0.7 msとなった。一方、造成コア約13.7 msと格子更新約6.5 msが残る。標高64 MiBと格子32 MiBを各更新でコピーする構成は変更していない。フレーム内の複数ポインタ点は標高コピーを複数回発生させる。長押しには処理時間とは別に150 msの反復間隔がある。

単体78件、Chrome/Edgeの通常回帰72件が成功し、重い任意検証16件はスキップした。比較計測は前後3件ずつ成功した。lint・型検査・ビルドとコードレビューも完了した。

## 推測・未確認事項

測定はCPU更新処理の時間であり、実際に画面へ提示される遅延やfpsの保証ではない。全端末・複雑な海岸・大半径への保証でもない。滑らかな操作へ向け、1更新16〜33 msを評価目安とし、中央値だけでなく95%点と初回応答を継続計測する。

次の候補はフレーム内のポインタ経路を維持した処理の統合、標高・格子のタイル化または差分更新による全体コピー解消である。LOD詳細化の切替と海岸線更新のスパイクも別途評価する。immutableキャッシュとUndo/取消を維持する必要がある。

## 結果どうしたか

外周の表示不具合を修正し、チャンク部分更新と初回検査キャッシュを導入した。操作全体の時間に加えて、更新単位の内訳と分位点をローカル計測できるようにし、通常の操作計測JSONにも更新内訳を保存する構成にした。
