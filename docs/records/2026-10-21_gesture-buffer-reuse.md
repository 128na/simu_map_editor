# ドラッグ造成中の配列再利用による更新遅延の削減

## 目的 / 発端

4096四方の連続造成について、前回の描画部分更新後も標高64 MiB・表示格子約32 MiBの全配列コピーが更新ごとに残っていた。Wasm導入を検討する前に、計測上の主要負荷であるコピーそのものを削減する。

## 分かったこと（事実）

造成開始前のマップは不変のまま保持し、最初に実際の編集が発生した時だけ作業用配列を複製する方式を実装した。同じジェスチャー内の後続点・同一フレーム内の複数点・長押しでは、その配列を再利用する。全入力経路と平滑化の逐次適用を維持し、点の間引きや順序変更はしていない。確定時にセッションを閉じ、以後の編集は別の配列を使う。Undoは開始前との疎な差分を保存する。

表示格子は変更領域の前後値だけを保持して直接更新する。海面再生成の判定は更新前に行い、格子適用後に水面・地形の準備が失敗した時は保存領域を復元する。外周の複製頂点も変更領域に含める。

Chrome / RTX 4070 Ti、4096四方の平坦地、半径8、41点の同じ曲線入力で変更前後を各3回測定した。変更前はbbb4b0aのクリーンな状態、変更後はその上の今回の作業ツリーであり、旧モジュールの差替えは利用していない。[生データ](2026-10-21_gesture-buffer-results.json)のafter内のrevisionは計測時のベースコミットで、実装後コミットの識別子ではない。各試行の指標の中央値は次のとおり。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 初回更新 | 31.0 ms | 20.1 ms |
| 連続更新の中央値 | 21.5 ms | 1.2 ms |
| 連続更新の95%点 | 25.9 ms | 2.5 ms |
| 連続更新の最大値 | 40.6 ms | 18.7 ms |

移動更新をまとめた処理内訳の中央値は、造成コア13.7→0.5 ms、格子更新6.6→計測精度上0.0 ms、描画更新0.7→0.5 msだった。格子の処理が完全にゼロになったという意味ではない。

## 推測・未確認事項

Wasmは今回導入していない。この結果は、今回の主な負荷を減らすうえで言語移行が必須ではなかったことを示す。Wasmによる数値計算の改善幅は測定していない。

更新の計測範囲はCPU処理であり、入力から画面へ提示されるまでの遅延やfpsを保証しない。初回は標高全体の複製が残り、最大更新時間も約19 msだった。大半径・高い山の斜面補正・海岸の編集・LOD境界切替には別の負荷がある。水面全再生成、初回複製、Undo時の全体変換、メッシュ詳細化の切替が今後の評価候補になる。

## 結果どうしたか

標高の再利用は所有権を限定したジェスチャーAPI内へ閉じ込め、従来の不変な単発編集APIは維持した。格子は同期トランザクションとして更新・復元し、取消と履歴登録拒否時は開始前マップへ戻す。変更前後の全ブラシ・斜面1/2の結果比較、原本不変性、確定後の編集禁止、格子の完全変換との一致、水面判定とロールバックを検証するテストを追加した。

モジュール差替え式の性能比較にはAPI互換性が必要になったため、非互換な旧SHAはブラウザ起動前に説明付きで拒否する。APIが異なる版は各チェックアウトで直接計測し、JSONを保持して比較する。

単体82件、Chrome/Edgeの通常回帰74件が成功し、任意の重い検証16件はスキップした。4096四方の応答計測は前後各3件成功した。lint・型検査・ビルドとレビューも完了した。複数更新の曲がった経路、Escape、履歴予算拒否のブラウザ検証で、標高と格子の完全復元を確認した。
