# 分割境界の深い側面と大ブラシ掘削の負荷

## 目的 / 発端

利用者から、最小標高より深い格子状の表示が残ること、ブラシ40の掘削が重いこと、カーソルから離れた地形がぼやけることが報告された。前回は外周の側面だけを除去し、小ブラシ・盛土の性能を主に計測していたため、内部境界と海岸線を動かす大ブラシの問題を拾えていなかった。

## 分かったこと（事実）

内部のチャンク境界には高さ−256までの側面が残っていた。全ての側面を除去し、表示間隔が異なるチャンクも境界で実際の標高を1タイルごとに共有する接続へ変更した。粗い境界セルにだけ三角形を追加する方式で、内部全体を細分化せず隙間を防ぐ。境界法線と追加頂点の部分更新も完全再生成と比較した。

カーソルに合わせて直ちに詳細化・粗視化する方式だったため、最近編集した最大12チャンクの詳細表示を保持する構成へ変更した。カーソル周囲最大4チャンクと合わせて最大16チャンクに制限する。遠方の未編集範囲は引き続き概略表示であり、マップ全体の常時詳細表示ではない。

ブラシ40・強さ8・掘削で海面をまたぐと、水面の全体再生成が各更新の大部分を占めていた。水面を256タイル単位に分割し、変更頂点に接するセルを含むチャンクだけを準備・差替えする方式へ変更した。水面は従来の三角形単位クリッピングを使い、奇数寸法でもマップ全体と同じ座標へ配置する。全チャンク合計のCPU配列16 MiB制限は維持し、準備が失敗した時は既存の水面を変更しない。

4096四方の平坦地、既定互換プロファイル、ブラシ40・強さ8・掘削、同じ41点の経路をChrome / RTX 4070 Tiで変更前後各3回計測した。変更前は35b536dへ水面計時とブラシ設定の計測コードだけを加えた状態、変更後は今回の作業ツリーである。モジュール差替えは行っていない。各試行の指標の中央値は以下のとおり。[生データ](2026-10-21_large-brush-water-results.json)のrevisionは計測時のベースコミットである。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 初回更新 | 404.7 ms | 33.8 ms |
| 連続更新の中央値 | 413.8 ms | 5.9 ms |
| 連続更新の95%点 | 454.9 ms | 15.8 ms |
| 連続更新の最大値 | 474.0 ms | 21.2 ms |

移動更新をまとめた処理内訳の中央値では、水面処理411.15→3.8 ms、造成コア1.0→1.0 msだった。今回のケースは主に水面再生成の削減が効いた。

## 推測・未確認事項

計測はCPU更新時間で、入力から画面提示までの遅延やfpsの保証ではない。小ブラシだけの計測から全ブラシ・海岸線編集へ性能を一般化できない。初回複製、LOD境界切替、高い山や複雑な海岸線の編集には残る負荷がある。全面が海のマップは分割数に応じた水面描画命令が増えるため、GPU側の評価も別途必要になる。

詳細保持には上限があり、古い編集領域は多数のチャンクを編集すると概略表示へ戻る。全景で全ての1タイル凹凸が見えることを保証する構成ではない。

## 結果どうしたか

深い側面を実標高に沿った境界接続へ置き換え、最近編集した範囲の詳細を保持し、水面を部分更新へ変更した。性能検証はブラシ半径・強さ・盛土／掘削を指定でき、水面処理時間も記録する。水面のクリッピング・合計予算・失敗時の原状保持と、地形境界の一致・面積・上向き三角形・詳細保持上限・部分更新結果を単体検証する。

単体90件、Chrome/Edgeの通常回帰76件が成功し、任意の重い検証16件はスキップした。1025四方の斜め画像で深い格子がないことを確認し、カーソル移動後の編集チャンクの表示間隔1をブラウザ検証した。大ブラシ比較は前後各3件成功した。小ブラシ半径8・盛土・強さ1の確認計測1回は中央値1.2 ms・95%点3.0 msだった。lint・型検査・ビルドとレビューも完了した。
