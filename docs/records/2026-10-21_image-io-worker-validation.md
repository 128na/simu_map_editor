# 大サイズ画像変換の取消と応答性検証

## 目的 / 発端

Issue #5の大サイズ画像処理について、変換中の応答停止と取消・失敗による編集状態の破損を検証した。

## 分かったこと（事実）

平坦な4096・8192四方でBMP/PNGを各1回比較した。旧メインスレッドの直接変換では最大RAF間隔が4096で951〜1668ms、8192で3720〜6522msだった。Worker経由では4096で17ms、8192で50〜67msだった。

|サイズ|形式|Worker書出全体ms|Worker読込全体ms|
|---|---|---:|---:|
|4096|BMP|137|1733|
|4096|PNG|145|1731|
|8192|BMP|522|6774|
|8192|PNG|549|6712|

これは変換経路の比較であり、全操作の高速化率ではない。確認ダイアログ・テスト画像生成・最終描画反映は含まない。平坦地形の単発計測なので複雑な画像や他環境の保証には使えない。再現用コマンドを `npm run benchmark:image-io` として追加した。JSONの配列サイズは名前付き配列の部分見積もりであり、同時ピークやプロセス全体の実測ではない。BMP出力行と出力ファイルは同じ配列を指す。

ChromeとEdgeで取消・失敗・置換競合・同一ファイル再試行・PNG往復の14件を実行し、全件成功した。Workerの実際のコードに読込遅延・圧縮遅延・割当失敗・起動失敗を注入し、地形全体・格子・互換設定・履歴・保存状態の保全を比較した。サービスの単体検証6件も成功した。

固定Simutransソースのネイティブ検証は240ケース・15画像で成功し、ブラウザからの実ローダー比較・外周造成書出・全対応プロファイルのPNG比較3件も成功した。変換Workerは既存コーデックと正規化を再利用しており、互換計算は変更していない。

独立レビューでは必須修正なし。配列サイズの二重計上を避ける注記を追加した。

## 推測・未確認事項

最終描画反映の同期処理とGPU側の割当失敗はこの変換計測では評価していない。Workerで変換が完了しても、最終反映には大きなメインスレッド処理が残り得る。描画反映の計測と履歴資源不足の検証を続ける。

## 結果どうしたか

[ADR-0021](../adr/0021-cancellable-image-conversion-worker.md)に従い、段階表示と取消を追加した。書出失敗・取消は保存済みにしない。通常CIにも画像入出力の回帰検証を加え、大サイズ性能計測はローカル任意実行とした。
